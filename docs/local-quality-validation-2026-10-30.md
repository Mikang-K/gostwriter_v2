# 로컬 소설 생성 개선 및 검증 — 2026-10-30

## 판정

**문맥 전달 개선은 검증했지만, 소설 품질 개선은 입증하지 못했다.** 최종 비교에서
문체 예시가 모든 요청에 전달되고 출력 절단은 없었으나, 분량 지시 준수는 오히려 낮아졌다.
문체 예시의 사건 혼입, 부자연스러운 한국어, 반복이 남았다. 이 결과로 기본 모델을 변경하지 않는다.

## 구현

- `backend/app/context.py`: 첫 생성·이어쓰기·에필로그 모두 문체 참고를 사용한다.
  예시마다 앞 300자를 사용하며, 첫 예시와 최신 원문의 끝 500자를 우선 배치한다.
  더 오래된 원문은 직접 넣지 않고 기존 회차 요약으로 제공한다.
- 사건·시점·분량·종료 지점을 따르고, 별도 범위 지시가 없으면 한 장면에 집중하도록 안내한다.
  문체 예시의 사건·사물·문장 복사를 금지한다. 현재 지시는 참고 자료 뒤에 둔다.
- 필수 설정과 메모리를 자르지 않는 정책, UTF-8 바이트 기반 보수적 예산 계산,
  에필로그 지시, 외부 전송 동의 정책을 유지했다. 토큰 추정기를 임의 비율로 완화하지 않았다.
- 전개 방향 입력란과 README에 장면 단위 요청 예시를 추가했다.
- `scripts/quality-compare.py`: 설치된 Ollama 모델에만 합성 입력을 보내고,
  입력·출력·모델 digest·코드 SHA256·종료 사유를 보존한다. 기존 결과를 덮어쓰지 않는다.
  HTTP 오류나 출력 절단은 실패 처리한다. 사람 평가 점수는 생성하지 않는다.

## 실제 모델 비교

기준 코드는 HEAD `7c5f5346bbcaa939a71cd43e80a53f2f8683254c`의 수정 전 문맥 구성 함수다.
합성 미스터리 이야기의 첫 장면·이어쓰기·6회차 이력 조건을 각각 seed 42·43으로 비교했다.
이력 조건에는 반복되는 과거 원문을 넣어 반복 전염을 관찰했다. 실제 사용자 원고는 사용하지 않았다.
장편 독서 경험을 재현한 평가는 아니다.

공통 조건: context 8192, 출력 상한 1024 tokens, temperature 0.7, 250~400자 요청.
각 모델·조건·시드에서 수정 전후에 같은 설정·전개 방향을 전달했다. 홀수 시드는 실행 순서를 뒤집었다.
서로 다른 시드도 같은 장면이므로 독립적인 6개 작품으로 해석하면 안 된다.
시드가 같아도 모든 실행이 바이트 단위로 동일하지는 않았다. 콜드/웜 성능 비교는 하지 않았다.

### 최종 비교(run-2)

| 모델 | 문맥 구성 | 출력 수 | stop / length | 요청 분량 250~400자 | 문체 예시 입력 포함 |
|---|---|---:|---:|---:|---:|
| Gemma 1B Q4 | 수정 전 | 6 | 6 / 0 | 2/6 | 2/6 |
| Gemma 1B Q4 | 수정 후 | 6 | 6 / 0 | 1/6 | 6/6 |
| Gemma 4B Q4 | 수정 전 | 6 | 6 / 0 | 4/6 | 2/6 |
| Gemma 4B Q4 | 수정 후 | 6 | 6 / 0 | 1/6 | 6/6 |

분량은 Python `len(body)`로 공백·개행을 포함해 셌다. `stop`은 정상적인 전송 종료이며
문장력·설정 준수의 합격 판정이 아니다. 문체 예시 입력 포함 역시 문체 재현을 보증하지 않는다.

4B 이력 조건(seed 42)의 문맥 추정량은 5665에서 2624로, 공급자 보고 입력 토큰은
1618에서 699로 줄었다. 이는 과거 원문을 요약으로 대체한 결과이며 품질 향상률이 아니다.

### 출력에서 관찰한 문제

아래는 에이전트가 원문을 읽고 기록한 관찰이다. 사람의 블라인드 평가를 대신하지 않는다.

- 1B 수정 후 이어쓰기(seed 42): `하린은 문고리 밑에서 젖은 봉투를 꺼내 들었다.`
  “봉투는 아직 찾지 못한다”는 지시를 위반했다.
- 4B 수정 후 이어쓰기(seed 43): `초침은 멈추지 않고, 같은 자리에 서 있었다.`
  동작 묘사가 모순된다. 입력 문체 예시에 있던 열차 대사가 이어쓰기에도 섞였다.
- 4B 수정 후 이력 조건(seed 42): `시곇 바퀴가 긁는 소리는 역무실 침묵을 깉게 만들었다.`
  어휘·철자 오류가 남았다. 수정 전에도 `바닥을 더 밀짚처럼 훑었다` 같은 어색한 표현이 있었다.
- 최종 수정 후 출력의 분량 준수는 합계 2/12로 수정 전 6/12보다 낮았다.
  문맥 수정이 전반적인 지시 준수까지 높였다고 결론 낼 수 없다.

첫 실험(run-1)은 24회 중 1B 수정 후 이력 조건(seed 43)에서 반복 끝에 1024-token 절단이 발생했다.
이를 계기로 과거 원문 직접 전달을 제거하고 문체 자료의 사건 혼입 금지 지시를 보완했다.
최종 run-2는 24회 모두 stop으로 끝났다. 두 실험 총 48회 호출은 모두 로컬 Ollama였다.
개선안 선택에 사용한 같은 사례를 다시 측정했으므로 별도 미사용 사례 검증이 필요하다.

## 회귀 및 기능 검증

- 새 회귀 테스트: 수정 전 5실패·2통과, 수정 후 문맥·메모리 관련 9통과.
- 백엔드 전체: **110통과**. 초기 실행은 DB 미기동으로 2개 setup 오류가 났고,
  기존 로컬 PostgreSQL을 시작한 후 전체 재실행에서 통과했다.
- 프런트 단위: **7통과**. TypeScript·ESLint·Ruff·`git diff --check` 통과.
- 실제 Gemma 4B + 격리 PostgreSQL smoke: 생성 성공, 본문과 메모리 원자 저장 및 재조회 일치.
  이 smoke는 짧은 첫 장면 기능 검증이며 문체 평가가 아니다.
- pytest 캐시 쓰기 권한 경고는 남았으나 테스트 실패는 없었다.
- 프런트 빌드: 기존 `node_modules`·`.next` junction 때문에 최초 빌드는 런타임 모듈을 찾지 못했다.
  해당 명령 프로세스에만 `NODE_PATH`를 지정한 재실행은 통과했다. 설정 파일은 변경하지 않았다.
  외부 경로의 27개 파일이 standalone 출력에서 제외된다는 경고가 있어 배포 패키지 검증은 별도다.
- 브라우저: Chromium 5통과, Firefox 4통과 후 마지막 테스트의 trace 저장 단계에서
  OneDrive 작업 경로 `EPERM` 발생. 해당 Firefox 테스트만 임시 폴더 출력으로 재실행해 1통과했다.
  따라서 총 10개 브라우저 사례를 확인했지만 최초 전체 명령은 종료 코드 1이었다.
  최초 빌드 전 E2E 시도도 서버 준비 시간 초과로 실패했다. 결과 경로의 권한 문제를 제품 버그로
  분류하거나 환경 우회 재검증을 최초 실행 성공으로 바꾸지 않는다.

커밋 전 재검증에서는 백엔드 110개·프런트 단위 7개·Chromium 5개·Firefox 5개가 모두 통과했다.
브라우저 결과를 새 임시 폴더에 기록한 전체 명령은 종료 코드 0이었다. TypeScript·ESLint·Ruff와
문서 링크·비밀정보 패턴 검사도 통과했다. 실제 모델 비교는 반복 실행하지 않았으며,
현재 문맥 코드의 SHA256이 최종 비교 manifest와 일치함을 확인했다.
